Home Assignment
Build a Configurable Distributed Rate Limiter
1. Problem statement
Our platform exposes APIs consumed by multiple clients, including mobile applications, web applications and internal services.
As usage grows, we need a mechanism to control incoming API traffic based on configurable policies.
Build a service that allows the platform to define and enforce request policies for different consumers and APIs.
The system should provide a clear response for incoming requests based on the applicable policies.
You may make reasonable assumptions about functionality that is not explicitly defined. Document these assumptions as part of your
submission.
For example:
● A regular user can make 100 requests per minute.
● A premium user can make 500 requests per minute.
● Different API endpoints can have different limits.
● Rate limits should be consistently enforced even when requests are handled by multiple application instances.
Your task is to build a working implementation of this rate-limiting service.

2. Functional expectations
Your solution should provide the ability to:
1. Define and manage request policies.
2. Associate policies with different consumers and APIs.
3. Evaluate incoming requests against applicable policies.
4. Communicate the outcome of request evaluation.
5. Provide relevant information to callers when a request cannot be processed.
You may introduce additional capabilities where you believe they are necessary.

3. Technical requirements
● Language: Java or Python.
● Databases: PostgreSQL and Redis.
● Local execution environment.
● REST APIs.
● Automated tests.
You have flexibility in choosing frameworks and libraries.
Any significant deviation from the suggested technology choices should be explained in your documentation.

4. Engineering expectations
We are interested in your engineering decisions, not just the final functionality.
You do not need to implement a production-grade distributed infrastructure. Prioritise a correct, understandable and maintainable solution.

5. Design decisions
We deliberately do not prescribe the implementation approach.
You should decide and document design decisions and architecture choices that you considered and rejected.
We are interested in understanding why you selected your approach and what trade-offs it introduces.

8. Local execution requirements
The solution should be executable on a developer's laptop without complicated setup.
Expected dependencies:
● Java or Python runtime.
● Local PostgreSQL.
● Local Redis.
Suggested execution experience:

./run.sh

# Execute tests
./test.sh
You can provide equivalent commands for your chosen language.
The README should explain prerequisites, configuration, startup, test execution and sample API requests.
Please avoid:
● Cloud infrastructure.
● Managed databases or Redis services.
● Kubernetes.
● Paid third-party services.
● Complicated multi-service deployment.
● Dependencies requiring external API credentials.
The evaluator should be able to clone the repository and run the solution locally with minimal effort.
